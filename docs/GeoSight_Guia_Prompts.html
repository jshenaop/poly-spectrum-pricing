# GeoSight Platform — Polygon Spectrum Pricing

![Tests](https://github.com/jshenaop/poly-spectrum-pricing/actions/workflows/tests.yml/badge.svg)
![Python](https://img.shields.io/badge/python-3.11-blue)

![License](https://img.shields.io/badge/license-Private-red)

**Plataforma de análisis geoespacial de Antigravity.**
Consulta datos de cobertura sobre polígonos colombianos, calcula valoración
por área y visualiza coberturas en mapas interactivos.

---

## ¿Qué hace GeoSight?

| Función | Descripción |
|---|---|
| 🗺️ Visualización interactiva | Mapas Folium con círculos de cobertura coloreados |
| 📐 Radios de cobertura | 4.6 km · 12.02 km · 19.64 km seleccionables |
| 💰 Valoración geoespacial | `valor = Σ (cop_ipm_mhz_hab_anio × personas)` por polígono dentro del círculo |
| 📊 Reporte ejecutivo | Costo Total por Área (COP) y Población Cubierta |
| 📥 Exportación | Mapa como HTML · Reporte como CSV |

```
Backend      →  Python 3.11 + FastAPI
Geoespacial  →  GeoPandas + Shapely (STRtree)

Datos        →  n6_1k_aniop_ipm.geojson (local, NO en Git)
Containers   →  Docker + Docker Compose
CI/CD        →  GitHub Actions
AI Dev       →  Claude Code
```

## Formato de Datos

El archivo `n6_1k_aniop_ipm.geojson` requiere estos campos en `properties`:

| Campo | Tipo | Descripción |
|---|---|---|
| `cop_ipm_mhz_hab_anio` | `float` | Costo en COP por MHz por habitante por año |
| `personas` | `int` | Población del polígono (puede ser 0) |

FASE 01 · INFRAESTRUCTURA
Docker & Environments
El entorno de ejecución. Un Dockerfile bien construido significa que GeoSight funciona igual en tu PC, en la PC del cliente y en producción. Los Environments separan dev, staging y prod.
🎓
Principio fundamental: En desarrollo local usamos docker-compose.override.yml (no está en Git) que agrega hot-reload. En producción usamos docker-compose.production.yml (sí está en Git, pero sin secrets). Docker lee el override automáticamente cuando existe — no tienes que especificarlo.

03
Agregar NGINX como reverse proxy
Web Server
🎓
¿Por qué NGINX frente a Uvicorn? Uvicorn es excelente para Python async, pero no está diseñado para ser el servidor público. NGINX maneja miles de conexiones simultáneas eficientemente, sirve archivos estáticos sin tocar Python, agrega gzip, rate limiting y SSL — todo sin que FastAPI lo sepa. En producción la diferencia es de 10-20x en throughput de archivos estáticos.
claude · fase-1 · nginx
# Agrega NGINX como reverse proxy al stack de Docker Agrega NGINX 1.25-alpine al stack de GeoSight como reverse proxy: 1. Crea el directorio nginx/ con dos configs: nginx/nginx.conf (desarrollo): - upstream app { server app:8000; } - listen 80 - location /static/ { alias /app/static/; } - location / { proxy_pass http://app; proxy headers } - logs a stdout/stderr para Docker nginx/nginx.prod.conf (producción): - Todo lo anterior más: - gzip on para text/html, application/json - client_max_body_size 10m - add_header X-Frame-Options SAMEORIGIN - add_header X-Content-Type-Options nosniff 2. En docker-compose.yml agrega el servicio nginx: image: nginx:1.25-alpine ports: "80:80" volumes: ./nginx/nginx.conf, ./app/static:/app/static:ro depends_on: app restart: unless-stopped El servicio app NO expone puertos al host (solo red interna) 3. En docker-compose.production.yml sobreescribe el volumen para usar nginx.prod.conf en vez de nginx.conf 4. En Dockerfile agrega el directorio static/ en WORKDIR para que NGINX pueda montarlo como volumen 5. Actualiza el health check: GET http://localhost/health (ya no http://localhost:8000/health) Muéstrame el nginx.conf y el docker-compose.yml final.

🎓
¿Por qué NGINX frente a Uvicorn? Uvicorn es ideal para Python async, pero no está diseñado para ser el servidor público. NGINX maneja miles de conexiones simultáneas eficientemente, sirve archivos estáticos directamente desde disco sin tocar Python, agrega compresión gzip y rate limiting. En producción la diferencia es de 10-20x en throughput de archivos estáticos. Uvicorn queda en la red interna de Docker — el mundo exterior solo ve el puerto 80 de NGINX.

01
Crear geo_engine.py con la fórmula de valoración
Core
🎓
¿Por qué STRtree? Sin el índice, para cada query tienes que revisar TODOS los polígonos del JSON uno por uno. Con 10,000 polígonos eso son 10,000 comparaciones por click. STRtree reduce eso a ~50-100 candidatos antes de la comparación exacta. La diferencia es 500ms vs 15ms.
claude · fase-2 · paso-01
Crea app/geo_engine.py con la clase GeoEngine: 1. __init__(self): - Carga el JSON desde la ruta en GEOSIGHT_DATA_PATH - Construye un STRtree sobre las geometrías - Guarda en memoria (NO recargar en cada query) - Si el JSON no existe, loguea WARNING y no falla 2. calculate_coverage(lat, lng, radius_km) → dict: - Convierte el punto a buffer circular en metros - Usa STRtree para filtrar candidatos - Para cada candidato que .within(buffer): valor += cop_ipm_mhz_hab_anio * personas población += personas - Retorna: {total_value, population_covered, polygon_count} IMPORTANTE: solo polígonos completamente dentro del círculo (within), sin ponderar por área 3. VALID_RADII = [4.6, 12.02, 19.64] como constante de clase 4. Docstrings en español. Manejo de errores explícito. Al terminar, crea tests/test_geo_engine.py con 3 tests básicos: - test que radius inválido lanza ValueError - test que cálculo con fixtures da resultado conocido - test que STRtree está inicializado
✅
Resultado esperado: geo_engine.py creado con STRtree, fórmula v3.1 y regla within implementadas, 3 tests pasando en pytest.
